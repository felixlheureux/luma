# Local device backup inspection

Open **Backups** and choose **Inspect local backups**. This is an explicit, read-only check of the standard local iPhone/iPad backup location, `~/Library/Application Support/MobileSync/Backup/`. It is separate from Clean and is not included automatically in Overview scans. iCloud backups, linked/relocated backup roots, other users and other volumes are not inventoried.

Each immediate backup folder is one record. Luma shows the recorded device name when available, a recorded backup date, encryption information, logical size and metadata/read state. Device serial numbers, IMEI, UDID and raw backup-directory identifiers are not displayed in normal cards, notices or progress. Records have neutral ordinal labels; same-name devices are not merged, and no “latest usable backup” inference is made from a name or date. Reveal in Finder deliberately selects the actual folder.

Supported inspection is narrow. Recognized folder names are a 40-hex identifier or the modern 8-hex/16-hex hyphenated identifier, optionally followed by an archived date/time suffix. In those folders, only `Info.plist`, `Manifest.plist` and `Status.plist` may be read for content, at most 1 MiB each. The reader checks type/ownership/location/identity and hashes/rechecks these metadata bytes after sizing. It displays only the device name, recorded date and encryption flag. The recognized observed layout uses Manifest version `9.1` and Status version `3.3`. These are format observations from upstream backup implementations, not an Apple guarantee of completeness or restorability. Other layouts remain unrecognized; their contents are not interpreted. There is no private MobileDevice API, device connection, password request, decryptor, backup command or network request in the scan.

`Manifest.db` is checked only for the presence of a nonempty regular file, never opened as a database or for content. Payload files are not opened for content, decoded, decrypted, listed by domain or extracted. Descriptor metadata traversal measures logical bytes under the shared non-materializing/provider policy. The limit is 100 entries in the backup root, 200,000 sizing entries across all records, 64 levels and 1 MiB per summary plist. Ignored roots/backup folders/descendants, links/aliases/shared hardlinks, other owners/volumes, cloud/provider-managed content and denied capabilities fail closed. Unavailable sizes stay unknown rather than looking empty or reclaimable. Known sizes may include folders whose metadata is corrupt or unsupported; this is explicitly separate from metadata completeness. Root-list limits/access failures remain unavailable rather than claiming no backups.

States distinguish:

- **Metadata reports finished:** the recognized summary layout reports `SnapshotState = finished`, with the expected metadata and a nonempty manifest database. This does not verify database integrity, payload completeness, current idleness or a successful restore.
- **Incomplete or missing metadata:** required summary/database information is missing or the snapshot does not report finished.
- **Unrecognized or corrupt metadata:** malformed/oversized fields, wrong types, unknown versions/states or an unrecognized folder layout. Other readable observations may remain visible.
- **Empty folder:** the folder actually had no entries. This state does not authorize removal.
- **Changed during inspection**, **Inspection unavailable** and **Ignored:** the corresponding observation could not be established. Unknown size is not zero.

All backups are **Your files**, never ordinary generated caches. A stale date, encryption flag or missing/disconnected device does not show that a backup is expendable. No backup or internal chunk is selectable, no CleanupItem is produced, and the core explicitly rejects every path under the standard backup root and the backup rule namespace. This applies even to forged/manual plans, a reported-finished snapshot or injected activity observations. Global Library protection is retained.

This is the task's **inspection-only capability outcome**. The researched sources establish a backup location and metadata conventions, but they do not establish a supported macOS-wide backup/restore idleness check for Luma. Process observations can flag a known backup-related tool; no match still means **unknown**, never idle. No format/activity combination is therefore authorized for Luma Trash/Restore. There is deliberately no hidden fixture-only removal implementation or permissive activity override. A future removal proposal requires independent evidence and validation of its format, activity, whole-backup mutation and recovery contract; it is not silently enabled by a finished marker or process-name heuristic.

Use **Reveal this backup in Finder** or Apple's documented **General → Manage Backups** flow for available supported management actions. Check that you retain a usable copy before making changes. Finder changes are outside Luma Activity/Undo; Luma cannot claim recovery for them. Luma does not remove files, empty Trash, create a new backup or test a restore.

References checked on 2026-10-18: [Apple: locate and manage backups](https://support.apple.com/en-us/108809), [Apple: encrypted backups](https://support.apple.com/en-us/108353), [libimobiledevice's upstream backup reader/writer](https://github.com/libimobiledevice/libimobiledevice/blob/master/tools/idevicebackup2.c), and [pymobiledevice3's upstream backup implementation](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/mobilebackup2.py). Upstream code also demonstrates that a finished marker can exist before a transfer completes; it cannot be an idle signal. No third-party implementation is copied into Luma or installed as a dependency.
