# Developer project review

Open **Projects**, choose a project or a parent workspace folder, and inspect the results. Luma reads only the chosen tree, discovers supported manifests up to six directory levels, and keeps source, configuration, other data and excluded locations separate from cleanup candidates. Nothing is selected automatically. The system folder chooser grants the inspection scope; it does not authorize automatic cleanup.

The initial compiled rule set is version 1 (`project.v1.*`). These exact paths are supported:

| Ecosystem | Project evidence | Review candidate | Rebuilding or reinstalling |
| --- | --- | --- | --- |
| Node | A bounded JSON-object `package.json` | Project-local `node_modules` | Use the project's package manager, for example `npm install`. Network access and install scripts may be required; local edits and unavailable packages may not be recoverable by reinstalling. |
| Rust | Literal `[package]` or `[workspace]` table in `Cargo.toml` | Project-local `target` | `cargo build` recompiles output; missing dependencies may require network access. |
| Swift | Tools-version header, PackageDescription import and Package declaration in `Package.swift` | `.build/arm64-apple-macosx` or `.build/x86_64-apple-macosx` | `swift build` recompiles products; dependency resolution may need network access. |

These are static recognition rules, not full manifest parsers or a guarantee that every file is reproducible. Luma never evaluates manifests or runs package-manager, build, reinstall or configuration commands. Rust multiline-string manifests are conservatively unsupported. Custom output paths, target triples and environment-variable settings are not followed. Project source/manifests/lockfiles remain in place. Swift checkouts, repositories and downloaded artifacts remain excluded. Global stores, vendored folders, virtual environments and version-control metadata are not discovered as projects.

Every candidate is **Review**, including modified dependency contents. Build trees containing recognizable source or project configuration are excluded. A candidate containing a symbolic link (including an internal `.bin` link), Finder alias, hard-linked file, ignored descendant, provider-managed content, another owner/volume, recognizable credential/database/virtual-machine data or a vendored/shared store is excluded as a whole. Thus many npm workspaces, pnpm layouts and Swift trees containing symlinks intentionally remain unavailable for cleanup. Open those locations in Finder. There is no partial removal of a linked dependency tree. Unknown custom contents cannot be proven reproducible; inspect the candidate before selecting it.

Discovery stops after six levels, 10,000 directories or 20,000 discovery entries. A directory has a 10,000-entry discovery limit. Each candidate has a 100,000-entry/128-level inspection limit; non-candidate breakdown entries have a 20,000-entry inspection limit. Exclusions and incomplete sizes are explicit and are never reported as zero. Nested projects are listed separately; output/dependency directories are not searched for more projects. The cleanup plan rejects overlapping paths and duplicate objects and accounts shared content once.

Cleanup retains the app’s home-directory scope: system/external-volume locations and projects inside generated, vendored or shared stores cannot authorize a move, even when explicitly chosen for inspection.

Select individual folders, review their consequences and confirm **Move to Trash**. The ordinary cleanup journal records moves in **Activity**, where Restore and session Undo use the existing identity checks and never overwrite a recreated destination. The scanner is read-only. Cleanup revalidates the selected path, chosen-root scope, project directory/manifest identity and SHA-256, current ignore list, provider capability, ownership, volume and full tree identity before moving. Active or unknown tool activity blocks cleanup. Node runtimes, Cargo/Rust tools, Swift compilers, Xcode, package managers and common build tools conservatively block all project cleanup while running, since this implementation does not infer a process's project from its working directory. Stop the tools yourself; Luma does not terminate them. The existing pathname-mutation/process-start race boundary still applies; these checks cannot prevent another process from starting immediately afterward.

Version 1 is compiled policy in `DeveloperProjects.swift`, separate from task 008's global generated-cache YAML. Extending it requires code review and positive/negative project fixtures. No remote catalog, script or user configuration can add cleanup paths. Completed project snapshots use the common scan lifecycle and are invalidated after cleanup/Restore; views never traverse the filesystem.

Ecosystem references checked on 2026-10-18: [npm folder layout](https://docs.npmjs.com/cli/v11/configuring-npm/folders/), [npm install behavior](https://docs.npmjs.com/cli/v11/commands/npm-install/), [Cargo build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html), [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html), and [Swift build scratch directory](https://docs.swift.org/latest/documentation/swiftlinux/building/). These describe conventional tool locations, not the contents or safety of a particular user's folder.
