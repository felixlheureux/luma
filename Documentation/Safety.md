# Safety model and current limits

Scanners produce immutable candidates; they cannot delete files. Each candidate contains its path, logical size, classification, scanner rule, ownership evidence, consequence, scan time, and a filesystem identity and metadata-tree digest.

The UI starts with no selections. A review sheet lists the exact paths and removal consequences, and requires explicit acknowledgement. Review builds an immutable core cleanup plan with a session ID, exact items, authorized roots, duplicate-group evidence, and verified logical totals. `CleanupJournal.execute` is the only cleanup entry point: it preflights the complete plan, then uses the Safety Engine to revalidate each item before recording an intent and again immediately before calling Apple’s `FileManager.trashItem(at:resultingItemURL:)`. There is no permanent-delete fallback.

## Validation

- Strict path-component boundaries; prefix collisions do not pass.
- Protected system locations and whole user folders cannot be removed.
- Generated data must match one of 22 project-owned rules. Profile-based rules accept only supported local profile names and exact cache leaves. Rule ownership and classification cannot be overridden by a candidate.
- Application relationships must use exact bundle identifiers in approved locations.
- Potential leftovers must have exact reverse-DNS identifiers in approved user Library locations. Installed apps and embedded helpers are indexed, and Launch Services checks owners outside those folders. Ownership is checked again before Trash; reinstalling an app invalidates its old leftover selections. Containers require matching owner metadata. Named support folders require an explicit project-owned mapping to a bundle identifier.
- Apple system applications and Luma itself are protected.
- Manual personal-file actions require an explicitly chosen folder inside the user’s home directory.
- Every path component is pinned with Darwin `openat`/`fstatat`/`fstat`, without following links. The saved location binds the exact path bytes to each ancestor's device, inode, owner and type. Replacing a parent invalidates cleanup even when the same target inode is moved back beneath it. Noncanonical dot-component paths, NULs and remote file URLs are rejected.
- Symlinks and Finder aliases in a candidate’s path are rejected. Only regular files and directories are supported. FIFOs, sockets, devices and other special objects are excluded before opening their data streams. Metadata handles use event-only/search-only access; hashing opens only a separately verified regular file.
- A directory containing a symbolic link is excluded, except internal framework links within an application bundle with verified, bounded Info.plist metadata. Link text and identity are fingerprinted; the tree walker does not descend through links. Resolved internal targets must remain within the same bundle and device, with no alias or link in their resolved path. External targets and aliases remain excluded.
- Tree records use length-prefixed byte fields and byte ordering. Delimiters, newlines, case and Unicode spelling cannot merge fingerprint records. The core does not case-fold or Unicode-normalize path authorization, location tokens or plan accounting keys. Filesystem-native equivalence (such as APFS normalization-insensitivity) still applies to lookups. Invalid UTF-8 filenames and trees deeper than 256 levels are unavailable for cleanup.
- File identity, device, ownership, modification time, size, and descendant metadata are rechecked. Results over 30 minutes old are rejected.
- Ignore rules override suggestions, including descendants of an ignored folder.
- A known running owning app blocks cleanup of its data. Package caches and developer data also check for active package managers and builds. Simulator cleanup requires a successful check that no devices are booted; an unknown state blocks cleanup. System-critical processes are not offered a Quit action.
- Plans reject repeated paths, repeated selected object identities, and parent/child overlap. Core callers cannot bypass this through an individual Trash method.
- Duplicate removal requires complete scanned group evidence and an independent, unselected keeper outside every selected subtree. Preflight and each duplicate move verify the selected file and keeper against the full SHA-256 digest; inaccessible or changed copies stop cleanup.
- Ignore and running-owner state are refreshed at execution boundaries. Plan IDs and per-item unique-byte contributions survive journal recovery. A used plan cannot be replayed; a new review is required.
- Cancelling, replacing or timing out a scan invalidates its event mailbox and never commits its partial output as an executable snapshot. Read-only previews and separately dated previous completed snapshots may remain visible. Cleanup review requires membership in the completed feature snapshot, then still revalidates the plan in the core.

## Meaning of totals

Sizes are logical bytes, not guaranteed reclaimed physical space. The verified review total counts hard-linked regular-file content once across the entire plan, including shared content in separate selected trees. Each journal record retains both its full item size and unique contribution; per-item sizes can therefore sum to more than the plan total. Hard links are also deduplicated within scanner trees; APFS clones, compression, snapshots, and filesystem sharing may affect actual savings. Available storage is macOS’s capacity for important usage and can include purgeable space. Moving files to Trash does not itself reclaim all their space.

Unreadable paths, links, and directories over the 250,000-entry per-item inspection limit are skipped with visible coverage notices. Duplicate scans are limited to 100,000 entries and exclude packages, hidden files, ubiquitous/cloud items, and different devices. External-volume cleanup is currently blocked. Some system-installed application bundles cannot be uninstalled because they are not owned by the current user.

## Early-build limitations

Descriptor-relative inspection rejects deterministic parent, object, type, owner and device replacements. The journal pins the source chain across final validation and the move, and checks the returned Trash object afterward when readable. Apple’s `FileManager.trashItem` still resolves a pathname: another process can change a name after the final check and before that API resolves it. Holding descriptors does not make this call atomic or prevent a wrong-object move in that residual window. An uncertain outcome retains its durable intent for Activity review; there is no permanent-delete or custom-Trash fallback. Metadata fingerprints are not content hashes for ordinary cleanup. Other processes can restart after an activity check. Process detection covers known executable and script names; custom wrappers can evade it. Quit owners and stop builds before cleaning.

Multi-item cleanup is not a filesystem transaction. An error stops further moves; earlier successes remain in Activity and Trash. Every Trash or Restore operation persists an intent before filesystem mutation. The journal holds an exclusive operation lock across the complete plan, including awaited context/progress updates, and rejects interleaved cleanup/Restore/reconciliation. It uses a private temporary file, file synchronization, and an atomic rename; completed history and removal of the intent are committed together. A later launch reconciles interrupted operations using device, inode, metadata, and location-independent tree fingerprints. It does not retry cleanup automatically. Unknown or ambiguous moves stay visible in Activity and pause further cleanup until reviewed.

macOS can allow moving an item to Trash while restricting direct Trash access. The journal preserves the location returned by macOS and the item's pre-move identity. Interrupted moves with unknown destinations require readable Trash metadata for reconciliation. Acknowledging an unresolved entry dismisses that intent without touching files.

Restore checks the saved identity against the current Trash item, rejects links, and verifies the entire original parent chain against the pre-Trash evidence. Sibling changes do not invalidate a parent; replacing its inode, owner, type or volume does. Restore uses Darwin `renameatx_np(RENAME_EXCL)` relative to pinned source and destination directories, with no overwriting, cross-volume copy or weaker fallback. Occupied destinations remain untouched, including a destination created immediately before the syscall. Directory descriptors anchor the rename, but another process can still replace the source basename after the last identity check. Post-move identity and parent-path checks retain the intent if the outcome cannot be verified; they cannot undo an already completed wrong-object rename.

The version-1 journal remains readable. The optional location evidence and new length-prefixed fingerprints apply to new scans; old interrupted operations use their original fingerprint encoding only for read-only reconciliation. Entries without parent-chain evidence require Finder Restore, because their historical parent identity cannot be reconstructed safely. New cleanup also requires a fresh scan rather than silently accepting older identity evidence. The app never empties Trash automatically.

The journal's file synchronization and atomic replacement protect against process interruption. Recovery after an operating-system or storage failure still depends on filesystem guarantees. Pathname validation is not a complete defense against a malicious process racing the final move. Ordinary cleanup fingerprints contain metadata, not file-content hashes.

These limits are release-hardening work. These remain development builds with the documented filesystem/provider and platform limits.

## Filesystem validation evidence

Task 002 adds deterministic synchronization fixtures for parent/ancestor replacement with a preserved target inode, target replacement, link substitution, changed Restore source/parent, occupied destinations and token replay at another hard-link path. A disposable case-sensitive APFS image verifies distinct case names, tree mount-boundary rejection and external-device cleanup rejection. Existing generated-data, leftover, duplicate and journal suites remain required.

`FilesystemIdentityTests.swift` contains a reusable metadata corpus: delimiter/newline and long names, Unicode spellings, hard links, a file created with a sparse logical range, POSIX permissions, ACLs, custom extended attributes and Finder-tag data. The opt-in native test sends only that generated corpus through the real journal/Trash/Restore boundary. Contents, identities, logical size, allocated-block counts and stored metadata are compared after restoration. Allocation may settle only after synchronization; these fixtures do not promise physical savings, cross-filesystem preservation, arbitrary ACL support, Finder tag presentation, unsupported objects or provider/cloud behavior. No external-volume mutation is enabled by these tests.

Run ordinary checks with `bash Scripts/test.sh`. Run the native corpus explicitly with `LUMA_NATIVE_TRASH_TEST=1 bash Scripts/test.sh`; it uses the current user's Trash for disposable generated files only. The optional `LUMA_EDGE_VOLUME_ROOT` must point to a disposable case-sensitive image mounted at `<fixture-home>/Downloads/Mounted`, inside the workspace. That test creates its own UUID child and also inspects the containing Downloads directory to prove that the nested mount is rejected. Never point it at personal storage.

## Scan sessions and cancellation

`ScanController` owns one detached utility worker, its operation ID, request/scope, progress, last-progress time, phase, cancellation handle and per-target completed snapshots. A replacement has one last-request-wins queue slot. It cancels the active job and waits for that worker to return before launching the replacement; repeated Cancel also clears the queue. Cancellation or a timeout cannot release the slot while a filesystem call is still executing. Late events from stopped workers are ignored and cannot clear another operation's busy state.

A coalescing mailbox publishes at most once per 150 ms, with previews capped at 1,500 cleanup locations, 5,000 app rows, 500 duplicate groups, 1,500 coverage rows and 200 notices. Full completed output retains the scanner's normal limits. Application metadata appears before recursive sizing; pending/unavailable sizes are distinct from measured zero. Folder items, footprints, leftovers and full-hash duplicate groups stream as read-only previews. A completed scan with exclusions may offer its fully inspected readable candidates; its skipped coverage and partial totals remain explicit. A cancelled, failed, replaced or timed-out scan never overwrites the prior completed snapshot.

Stall warnings are separate from total elapsed time and do not declare a read failed. Defaults are: duplicates warn after 30 seconds without progress, request a stop after 300 idle seconds or two hours total; inventory/overview use 20/180/3,600 seconds; other scans use 15/120/1,800 seconds. Full hashing reports progress between chunks, and filesystem traversal checks cancellation between entries/components. A blocked OS call can still take time to return; the UI stays in Stopping until it does. Bounds are defensive limits, not scan-completion promises.

Permission and skip coverage apply to all scanner families. A failed owner inventory stops leftover detection; it cannot silently establish orphanhood. Retry reuses the captured target, chosen folder or app. Permission guidance is shown for requested, blocked scopes, with a usable readable-results path; startup does not request broad access. The native QA uses disposable POSIX-denied folders to verify retry. System privacy/TCC settings changes and provider/network stalls need their own supported-environment checks.

Scan sessions keep the existing bounded traversal scopes. Task 047 now supplies the centralized provider/no-materialization policy described below, with explicit detection and integration-test limits. Scan cancellation does not add cleanup Stop or session Undo; those are task 048.

## Provider-aware access (task 047)

`FilesystemAccess` is shared by pinned traversal, recursive inspection, metadata reads, hashing, scanner discovery, cleanup and Restore. It checks every ancestor and leaf again when opening/revalidating paths. It excludes dataless flags, nonlocal volumes, reported ubiquitous items, system `Library/CloudStorage` and `Library/Mobile Documents` containers, and reported sync roots. Opaque File Provider/CloudDocs attribute names cause an unknown-access exclusion; their private contents are never interpreted. Missing/unreadable required metadata or unsupported extended flags also fail closed. An absent ubiquitous resource value on an ordinary local file is normal and is not itself proof of provider ownership or its absence.

Discovery, directory enumeration, reads, journal writes and synchronous move operations run inside `NonMaterializingIO.perform`, using Apple's thread-scoped `IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES` setting. The previous setting is restored before returning success or throwing, including cancellation. No scope spans an `await`, no detached worker inherits an assumed thread policy, and inability to establish the setting rejects the operation. `EDEADLK` from prohibited materialization becomes explicit online-only coverage. This prevents intentional materialization through the controlled thread; it cannot govern independent provider processes or eliminate final-call filesystem races.

A downloaded cloud item remains excluded. Skipped provider bytes are absent from inspected/logical cleanup totals rather than reported as zero-sized or reclaimable remote data. Coverage retains the access capability and offers an explicit Finder handoff. No Remove Download or cloud-deletion operation exists. Application/process views use generic app symbols instead of asking external icon services to inspect unverified file content; no file thumbnail or Quick Look pipeline is enabled. Future indexing/preview code must use this same boundary before reading content.

Detection has a defined platform limit: these public signals are not a universal inventory of arbitrary sync clients. Apple's `getIdentifierForUserVisibleFile` is scoped to the caller's File Provider extension and a negative response cannot establish that a file is unmanaged. It is therefore not used as local-only authorization. Custom/legacy synchronization outside system containers, with no reported sync-root, ubiquitous, dataless or provider-metadata signal, cannot be identified reliably; Luma does not claim universal cloud classification. External-volume cleanup remains unavailable independently. Real provider eviction/download, network mounts and relocated provider domains have not been integration-tested in this environment; fixtures exercise their rejected capability outcomes. A local capability means the current supported signals passed, not proof that no third-party process ever synchronizes that data.

An execute-only Trash directory can hide provider metadata even when a known filename can be reached. Reconciliation now retains that intent as unresolved until metadata is readable, rather than inferring local authority from object identity alone. Retrying reconciliation after access returns completes recovery without repeating the move. Ordinary readable local fixture Trash/Restore round trips remain supported.

Primary sources: [Apple TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files), the target SDK's `sys/resource.h`, `sys/stat.h`, `sys/attr.h` and `getattrlist(2)`, and [File Provider identifier lookup](https://developer.apple.com/documentation/fileprovider/nsfileprovidermanager/getidentifierforuservisiblefile(at:completionhandler:)).


## Early app cache batch (task 050)

Four new units are restricted to VS Code stable 1.142.0's verified default layout. Pinned installation metadata must agree on the bundle identifier, version, product name and released commit. Exact Cache, GPUCache, CachedData and logs directories are eligible units; no parent, descendant, session, settings, backup, shared container or arbitrary Electron app inherits that authority. Running owners/helpers and process evidence block execution; unavailable process evidence also blocks it. Diagnostics use Review first and explain that old logs cannot regenerate. The [support matrix](Cache-Support.md) records primary sources and explicit unsupported decisions, including sandbox containers and additional Xcode targets.

Generated scans retain a transient identity/size index. App/category/selection totals count hard links once within each displayed subset, and final plans recompute their selection. Cross-group hard links make group sums non-additive, which the interface explains. Mutation attempts and Restore invalidate generated results and both app/controller completed snapshots; this includes partial failures. A fresh scan is required. Test-only task-local roots and process snapshots isolate synthetic layouts from installed apps and are never configured by production flows. No privileged helper, cloud cleaning, real-app cleanup experiment or external rule loader was added.
